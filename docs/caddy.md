# Caddy 网关

这份文档说明 mac-manager 里的「Caddy 网关」管什么、怎么用、失败时是什么语义，
以及现在还没验证的部分。Caddy 本身仍是这台机器的常驻服务，mac-manager 不接管它的安装与运行。

## 管什么、不管什么

管：

- **受管区域里的转发规则**：新增、修改、启停、删除、把 Caddyfile 里已有的规则导入进来。
- 把这批规则**生成**成 Caddyfile 片段，并在你确认后写进文件、平滑加载、核实是否生效。
- 保留应用历史，可以把任意一次历史版本的规则恢复回去。

不管：

- Caddy 的安装、升级与二进制本身。
- 证书签发与续期、DNS 解析、Cloudflare 之类的上游服务。
- 任意 Caddy 指令的编辑（例如 `encode`、`redir`、`header`）；这类行属于「无法识别的行」，
  会让应用被拒绝，而不是被覆盖。
- Caddy 服务的启停（用「系统服务」页的 `com.freewind.caddy`，或 launchd 工具）。

## 受管区域机制

受管区域由站点块内的一对标记圈定：

```
	# mac-manager:rules:start
	# 本区域由 mac-manager 生成，手工改动会在下次应用时被覆盖。
	handle_path /alpha/* {
		reverse_proxy 127.0.0.1:15001
	}
	# mac-manager:rules:end
```

- 应用时**只替换两个标记之间的内容**，标记行本身、站点块、`tls` 行、全局选项块与注释
  **逐字节保持原样**；换行风格（LF / CRLF）按文件原样写回。
- 停用（`enabled: false`）的规则**不会写进文件**：停用一条规则再应用，等于把它的转发从
  Caddy 里移除，而规则本身仍留在数据库里，可以随时重新启用。
- 规则写进文件的顺序是数据库里的 `sortOrder`；导入时按文件里的出现顺序分配。

标记与生成逻辑分别在 [src/shared/caddy-format.ts](../src/shared/caddy-format.ts)（纯函数）
与 [src/server/caddy/apply.ts](../src/server/caddy/apply.ts)（写文件与加载）。

## 草稿与应用的区别

- **规则增删改与导入只写数据库**：不碰配置文件，也不产生应用记录。页面上的规则列表、
  搜索、启停都是这一类操作。
- **只有「应用变更」会写文件并重新加载 Caddy**：它先备份、再原子写入受管区域、然后
  `caddy reload`、最后核实运行配置。
- 判断状态用两个字段：
  - `hasUnappliedChanges`：数据库里的规则与「上次成功应用」的内容不一致（改名、改备注
    不算，因为不写进文件）。
  - `managedRegionDrifted`：文件里受管区域的内容与数据库规则不一致，通常意味着有人手工
    改过文件。为真时页面用持续提示警告，应用会覆盖这些手工改动。
- 页面还给出将要写入的正文（`previewText`）与五类变更（新增/修改/删除/启用/停用），
  确认对话框里写明变化条数，因此确认的是具体内容，不是一句「确定」。

## 接管步骤

新机器或还没接管时，页面会提示「现在不能应用变更」，原因是配置文件里还没有受管区域标记，
或者还有尚未接管的规则。接管步骤（**只列步骤，本轮不执行**）：

1. **备份 Caddyfile**，例如
   `cp ~/.config/caddy/Caddyfile ~/.config/caddy/Caddyfile.bak-$(date +%Y%m%d%H%M%S)`。
2. **把现有规则导入数据库**：在页面点「导入现有规则」。导入会识别文件里**所有**规则，
   不管它在不在标记内，因此导入与包标记的**顺序无关**：推荐的顺序是先导入、再加标记，
   但先把规则包进标记再点导入同样能导入成功（已存在的匹配条件会跳过）。
   导入只写数据库，不改文件。
3. **手工把同一批规则包进成对标记**：在站点块内、这批规则的前后各加一行
   `# mac-manager:rules:start` 与 `# mac-manager:rules:end`（缩进与规则一致，用制表符）。
4. **打开管理接口**：在全局选项块里把 `admin off` 改成 `admin 127.0.0.1:2019`。
   `admin off` 时无法通过管理接口热加载，初始化这次变更是它唯一必须重启的改动。
5. **重启服务**：`launchctl kickstart -k gui/$(id -u)/com.freewind.caddy`（或用
   `bun run ~/.agents/skills/launchd-service/scripts/launchd-service.ts restart caddy`）。
6. **回到页面核对**：确认「受管区域」显示已建立、没有未接管的规则、没有无法识别的行，
   并检查「变更预览」里的正文与你手工包进去的内容一致。
7. **点「应用变更」**：这一步会备份当前文件、写入受管区域、平滑加载并核实。

### 防止误清空的安全闸门

**从未成功应用过**、**数据库里一条规则都没有**、而**文件里的受管区域已经有规则**时，
应用会被拒绝（页面提示「数据库里还没有规则，但文件里的受管区域已有 N 条规则；请先导入
现有规则，避免应用后清空这些转发」）。否则一旦误点「应用变更」，受管区域里的转发会被
生成的空内容覆盖掉。点一次「导入现有规则」就能解除。

有成功应用记录后不再拦截：那时数据库是权威，用户可能确实想清空全部规则
（把规则逐条删掉再应用），不能误拦。

## 失败与恢复

应用是一个固定顺序的流程，每一步的失败语义都不同：

| 阶段 | 失败时的行为 | 用户看到 |
|---|---|---|
| 预检（受管区域、无法识别行、未接管规则、空库保护、指纹、管理接口可达、标记成对） | 不写文件、不留记录 | 409 与中文原因，「应用变更」按钮保持禁用 |
| `caddy validate` 校验候选配置 | 删掉临时文件，正式文件不动 | 400 与 caddy 输出的首行 |
| 备份 | 直接中止，不写文件 | 500，正式文件未变 |
| 原子写文件 | 目标文件未被改动 | 500，正式文件未变 |
| `caddy reload` 非 0 退出 | **自动把文件还原成备份内容**，不重试 | 500 与「配置未生效，文件已还原」 |
| `caddy reload` 超时或被信号杀死 | **不还原**（Caddy 可能已经加载） | 结果未知，提示核实后再决定是否恢复 |
| 核实运行配置（`GET /config/`）缺规则 | 记 `failed`，不报成功 | 消息列出缺失的上游/域名/路径 |
| 核实请求本身失败 | 记 `unknown` | 提示无法确认是否已生效 |

失败与成功都会在 `caddy_apply` 表里留下一条记录，页面「应用历史」按时间倒序列出：

- 状态用 Badge 区分：**已生效**（success）、**失败**（failed）、**结果未知**（unknown）。
- 「恢复此版本」会用该版本记录里的规则**整体替换**数据库规则，再走一遍应用流程
  （同样要备份、写入、加载、核实），因此恢复本身也会产生一条新记录。
- 结果未知时不要盲目重试：先看页面上的现状与历史，或恢复到一个已知版本。

## 备份位置

- 目录：`data/caddy-backups/`（相对项目根，见 [src/server/env.ts](../src/server/env.ts) 的
  `CADDY_BACKUP_DIR`）。
- 命名：`<yyyyMMddHHmmss>-Caddyfile`，即应用前的原文。
- 保留最近 **20** 份，超过时按文件名（也就是时间）删除最旧的。
- 同一秒内连续两次应用会覆盖同一个备份文件名，正常情况下两次应用之间文件已经变化，
  影响可以忽略。

## 限制与未验证项

- **手机安装、触控命中、PWA 安装态与真实浏览器渲染尚未验证**：页面只经过组件测试与
  typecheck/build 验证，没有在真机或浏览器里点过（本轮未启动浏览器）。
- **管理接口当前未启用**：本机 Caddyfile 里是 `admin off`，因此
  `http://127.0.0.1:2019` 不可达，页面会显示「管理接口不可达」并且**现在还不能真正应用**
  （先按上面的接管步骤操作）。
- 应用与恢复只在受控替身下验证过：`caddy validate` / `caddy reload` 都是替身，
  没有对真实配置跑过这两个命令。
- 页面不提供规则重排序；生成顺序由导入顺序（`sortOrder`）决定。
- 预览正文只是「将要写入受管区域的片段」，不是整份配置文件；站点块与全局选项块由你自己维护。
